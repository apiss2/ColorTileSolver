# 検証結果

作成時から v1.1.0 のリリース前までに行った検証を、実施した順に記録しています。各節に、その検証で使った環境と確認できた範囲を示します。

## 対象

2026年10月29日に作成した ColorTile Solver 1.0 の Windows x64版と、Windows版と共通で使うC++コードを検証しました。

Windows版はLLVM-MinGW 20261020でビルドしました。GUIの依存先はWindows標準のライブラリとWindowsに含まれるUCRTです。Python、Qt、追加のC++ランタイムDLLは配布物に必要ありません。

作成時の実行検証にはLinux上のWine 9.0を使用しました。この時点では、Windows 10／11の実機での操作は未確認です。以下に示す処理時間と手数は、この環境で観測した値です。すべてのPCや盤面で同じ結果になるとは限りません。

## 探索の正しさ

検証用に独立して実装した幅優先探索と、アプリの探索結果を比較しました。全消しできるかどうかと、全消しに必要な最小クリック数が一致することを確認しています。また、返された手順を再生し、それぞれのクリックでルールどおりにタイルを消せることも確認しました。

| 検証 | 件数 | 結果 |
|---|---:|---|
| 3×3、空白と2色の全組合せ | 19,683 | 全消し可否と最短手数が一致 |
| 3×4、4×4の乱数盤面 | 各500 | 全消し可否と最短手数が一致 |
| 別実装の参照探索による1色全組合せと3色乱数盤面など | 2,814 | 最短手数、消去対象、全経路の再生が一致 |

2,814件の参照比較はLinux版とWindows実行ファイルの双方で通過しました。これには元の実装で問題となっていた3枚のT字配置と、2色を2枚ずつ同時に消す配置も含まれます。

追加で、不正な色や盤面寸法を指定した場合の処理と、短い制限時間で探索が終了することを検証しました。探索の開始前と探索中にキャンセルした場合も確認しています。時間切れやキャンセルで探索を終えた結果は、最短性を証明したものとして扱わないことを確認しました。

## 添付画像の認識

提供された画像は641×440ピクセルです。23列15行の格子として読み取り、格子の位置を別途手動で指定して読み取った結果と比較しました。全345マスの色が一致し、タイルは200枚で各色20枚でした。色が不確かと判定されたマスは0件でした。

元画像を含む15種類の変換画像でも、すべてのマスの色が一致しました。拡大率0.5～3倍、余白追加、縦横比変更、盤面部分だけの切り抜き、JPEG品質95／85／70／50を含みます。JPEG品質50では2マスを不確かと表示しましたが、分類結果は一致しています。

無地の画像を盤面として受け付けないことを確認しました。画像の寸法、RGBデータを格納するバッファの長さ、格子の指定範囲が不正な場合の処理も検証しています。また、分類できない暗い色に対して警告が出ることを確認しました。

## Windows版のGUIを通した検証

GUIから画像を読み込み、探索を開始して結果を表示する一連の処理を実行しました。

| 入力 | 指定時間 | 結果 |
|---|---:|---|
| 今回の200枚の画像 | 2秒 | 75手の全消しを取得、最短性未確認と表示 |
| 同じ画像を別試行 | 2秒 | 73手の全消しを取得、最短性未確認と表示 |
| 同じ画像の短時間指定 | 0.15秒 | 77～78手の全消しを取得、最短性未確認と表示 |
| 3枚のT字配置 | 10秒 | 1手を最短確定、約0.007秒で終了 |
| 隣接する同色2枚 | 0.15秒 | 全消し不能と判定 |

200枚の画像を指定時間2秒で探索した試行では、約2.003～2.006秒で探索処理が終了しました。GUIの診断出力でも、認識した枚数、全消しの手数、残り枚数、最短性の表示、指定時間が画面と一致することを確認しました。

200枚の画像について、真の最短手数の証明には到達していません。このため、配布アプリと本報告では73手または75手を厳密な最短解として扱っていません。

日本語で画面が表示されることも確認しました。指定時間10秒の探索を途中で停止すると、それまでの手順が保持されました。その手順を前後に移動して確認し、最初の手順へ戻れることも検証しています。さらに、再探索と、計算中にウィンドウを閉じる操作を試しました。停止後に操作できるようになるまで約0.35秒かかり、再探索中に終了操作をした場合は約2.03秒で正常終了しました。これらもWineで観測した値です。

## 再現方法

[README.md](../README.md) のビルドとテストの項を参照してください。各テストの実装は次のファイルにあります。

- `tests/test_solver_exhaustive.cpp` は、盤面の全組合せについて探索結果を検証します。
- `tests/test_core.cpp` は、別実装の参照探索と結果を比較し、探索の停止処理も検証します。
- `tests/test_recognition.py` は、サンプル画像を変換して認識結果を検証します。
- `tests/test_gui_windows.cpp` は、GUIの操作とアプリの終了を検証します。

GUIの診断用引数も用意しています。

```powershell
.\ColorTileSolver.exe --smoke-solve 2 --capture gui.bmp .\examples\sample.png
```

指定時間の探索後に画面を保存し、`gui.bmp.json` へ認識枚数、手数、残数、最短性、指定時間と実行時間を書き出します。診断用の指定がない通常起動では、このようなファイルを自動作成しません。

## 1.1 の再生間隔と画面操作

2026年10月29日、追加機能を含むソースから再ビルドしました。Linux 側は GCC 13.3.0、Windows x64 側は LLVM-MinGW 20261020、CMake は 4.4.4 です。両方の CMake ビルドが成功しました。Windows 実行ファイルの依存先は Windows 標準 DLL と UCRT です。

Linux の CTest は `core_reference`、`solver_exhaustive`、`recognition_validation`、追加した `verified_screen_playback` の 4 件すべて成功しました。追加したテストでは、画面操作の状態が次のように変わることを確認しています。

- 全消しできる手順だけを受け付け、各クリックで消えるタイルが手順の記録と一致することを確認します。
- 実際の盤面が予定どおりに変わったことを確認してから次の手へ進み、指定したクリック間隔を守ります。
- クリック後に盤面の変化を確認できなければ停止し、同じクリックを再送しません。
- 手動で予定どおりにクリックすると、次の手を示すヒントが進みます。
- 画像認識が不確かな場合や、予定外の盤面変化が続いた場合は停止します。

この時点のWindows版の操作検証には、引き続き Linux 上の Wine 9.0 と専用の仮想デスクトップを使用しました。Windows実機での操作と、実際のブラウザゲームでの動作は未検証です。複数モニターと異なる表示倍率を組み合わせた実機構成も検証していません。

### GUI と再生間隔

`test_gui_windows` で、メニューバーの存在、旧ファイル操作ボタンの撤去、960×720 の最小サイズで主要操作部品が重ならないことを確認しました。Wine では他プロセスのメニュー項目情報を取得できなかったため、その環境に限って項目列挙の検査をスキップしました。通常の Windows で同テストを実行する場合は項目列挙も必須です。

間隔の入力欄では、上下の矢印で 0.1 秒ずつ変更でき、不正な数値を入力すると直前の有効な値に戻ることを確認しました。再生中に 1.0 秒から 0.1 秒へ変更すると速さが変わり、停止後には手順が進まなくなることも確認しています。この試行では、変更後に 5 手進むまで約 518msかかりました。探索の取り消しには約 330ms、探索中の終了には約 2,025msかかり、取り消した時点の 77 手の手順が保持されました。これらはこの環境で観測した値です。

### 画面取得とクリック入力

`test_desktop_windows` は別プロセスの専用ゲームウィンドウを起動し、そのウィンドウだけに実際の `SendInput` を送ります。初期盤面とクリック後の盤面の画像認識、ヒントによってフォーカスが移らないこと、ヒントを通して指定マスへクリックが届くことを確認しました。

指定範囲の外へのクリックを拒否することを確認しました。対象ウィンドウが移動した場合、別のウィンドウに隠れた場合、別のウィンドウが前面になった場合にも操作を拒否しました。記録したプロセス ID が一致しない場合と、対象ウィンドウが終了した場合も同様です。いずれの場合も、拒否した後に追加のクリックが届かないことを確認しています。画面操作テストでは、テスト自身が起動した対象だけを使い、私用の画面や既存アプリは操作していません。

### アプリ全体を通した画面操作

最終版の `test_screen_gui_windows` では、ドラッグ入力で実際に範囲を指定しました。その範囲から盤面を認識して探索し、ゲーム画面を操作して停止するまでを検証し、終了コード 0 で完了しました。実行環境には Wine 9.0 と Xvfb を使い、ウィンドウ管理には、アプリが指定した座標にウィンドウを配置する設定の TWM を使用しています。

| シナリオ | 確認結果 |
|---|---|
| 自動操作で全消し | 200枚の盤面を76クリックで全消し。実クリック数と手順一覧の76手が一致し、範囲外へのクリックは0回。 |
| ヒント表示 | 600msの待機中に自動クリックが0回。リングを通した手動クリック1回で次の表示へ進み、Escでリングが消えることを確認。 |
| 自動操作を途中でEsc停止 | 全消し前に停止し、停止確認後600msに追加クリックがないことを確認。 |
| 別ウィンドウへの切り替え | アプリを前面に戻すと自動操作が停止し、停止確認後600msに追加クリックがないことを確認。 |

この76手はテスト時に得られた全消し手順で、真の最短手数を証明したものではありません。テストの600msは停止後の観察時間であり、停止に要する時間の保証値ではありません。

対象ウィンドウを前面にする処理では、別プロセスへの通知が完了した後に、実際に前面になったか確認するようにしました。また、範囲選択にはマウスイベントに記録された座標を使います。描画待ちでイベントの処理が遅れても、ドラッグを始めた位置を保持できます。範囲選択用の画面を閉じた後に指定範囲を撮影し直して認識するため、選択開始時の古い画像を使って操作を始めることはありません。

範囲選択や最小化を検証するには、仮想画面でもウィンドウの位置を管理する必要があります。最終検証では、TWMを `UsePPosition "on"` に設定し、指定位置が維持される環境に揃えました。取得した画面が期待した内容と一致しなかった試行でも、盤面の不一致を検出し、クリックを始めずに停止することを確認しています。
