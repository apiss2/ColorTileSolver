# 検証結果

以下は作成時の検証記録です。ソース公開準備時の再検証結果は末尾に追記しています。

## 対象

ColorTile Solver 1.0。2026年10月29日に作成したWindows x64版と、その共通C++コードを検証しました。

Windows版はLLVM-MinGW 20261020でビルドしました。GUIの依存先はWindows標準のライブラリとWindowsに含まれるUCRTです。Python、Qt、追加のC++ランタイムDLLは配布物に必要ありません。

実行検証にはLinux上のWine 9.0を使用しました。Windows 10／11の実機での操作は未確認です。以下の速度は、この検証環境での観測値であり、すべてのPCや盤面で同じ時間と手数を保証するものではありません。

## 探索の正しさ

独立して実装した幅優先探索と比較し、全消し可能かどうか、全消しに必要な最小クリック数、返された各手の合法性を確認しました。

| 検証 | 件数 | 結果 |
|---|---:|---|
| 3×3、空白と2色の全組合せ | 19,683 | 全消し可否と最短手数が一致 |
| 3×4、4×4の乱数盤面 | 各500 | 全消し可否と最短手数が一致 |
| 別実装の参照探索による1色全組合せと3色乱数盤面など | 2,814 | 最短手数、消去対象、全経路の再生が一致 |

2,814件の参照比較はLinux版とWindows実行ファイルの双方で通過しました。これには元の実装で問題となっていた3枚のT字配置と、2色を2枚ずつ同時に消す配置も含まれます。

追加で、不正な色と盤面寸法、短時間の探索終了、開始前のキャンセル、探索中のキャンセルを検証しました。タイムアウトやキャンセルを最短性の証明として扱わないことも確認しました。

## 添付画像の認識

今回提供された画像は641×440ピクセルです。23列15行の格子として読み取り、全345マスについて、独立した手動位置指定による読み取りと一致しました。タイルは200枚で各色20枚、不確かな色の判定は0件でした。

元画像を含む15種類の変換画像でも、すべてのマスの色が一致しました。拡大率0.5～3倍、余白追加、縦横比変更、盤面部分だけの切り抜き、JPEG品質95／85／70／50を含みます。JPEG品質50では2マスを不確かと表示しましたが、分類結果は一致しています。

無地の画像は盤面として受理しません。画像寸法、RGBバッファの長さ、格子の範囲、未知の暗色の警告も検証しました。

## Windows版のGUIを通した検証

GUIから画像を読み込み、探索を開始して結果を表示する一連の処理を実行しました。

| 入力 | 指定時間 | 結果 |
|---|---:|---|
| 今回の200枚の画像 | 2秒 | 75手の全消しを取得、最短性未確認と表示 |
| 同じ画像を別試行 | 2秒 | 73手の全消しを取得、最短性未確認と表示 |
| 同じ画像の短時間指定 | 0.15秒 | 77～78手の全消しを取得、最短性未確認と表示 |
| 3枚のT字配置 | 10秒 | 1手を最短確定、約0.007秒で終了 |
| 隣接する同色2枚 | 0.15秒 | 全消し不能と判定 |

200枚の画像の2秒試行は、約2.003～2.006秒で探索処理を終えました。認識枚数、全消し手数、残数、最短性の表示、指定時間を、GUIの診断出力でも照合しました。

200枚の画像について、真の最短手数の証明には到達していません。このため、配布アプリと本報告では73手または75手を厳密な最短解として扱っていません。

日本語での画面表示も確認しました。また、10秒探索を途中で停止して手順を保持すること、前後移動、最初の手順への復帰、再探索、計算中にウィンドウを閉じる操作を検証しました。停止から操作可能になるまで約0.35秒、再探索中の終了は約2.03秒で、アプリは正常終了しました。これらもWineでの観測値です。

## 再現方法

[README.md](../README.md) のビルドとテストの項を参照してください。探索の全組合せテストは `tests/test_solver_exhaustive.cpp`、別の参照比較と停止処理のテストは `tests/test_core.cpp`、画像変換テストは `tests/test_recognition.py`、GUIの操作と終了の検証は `tests/test_gui_windows.cpp` にあります。

GUIの診断用引数も用意しています。

```powershell
.\ColorTileSolver.exe --smoke-solve 2 --capture gui.bmp .\examples\sample.png
```

指定時間の探索後に画面を保存し、`gui.bmp.json` へ認識枚数、手数、残数、最短性、指定時間と実行時間を書き出します。診断用の指定がない通常起動では、このようなファイルを自動作成しません。

## 1.1 の再生間隔と画面操作

2026年10月29日、追加機能を含むソースから再ビルドしました。Linux 側は GCC 13.3.0、Windows x64 側は LLVM-MinGW 20261020、CMake は 4.4.4 です。両方の CMake ビルドが成功しました。Windows 実行ファイルの依存先は Windows 標準 DLL と UCRT です。

Linux の CTest は `core_reference`、`solver_exhaustive`、`recognition_validation`、追加した `verified_screen_playback` の 4 件すべて成功しました。新しい状態遷移テストでは、全消し手順以外の拒否、削除対象の照合、画面変化の確認、クリック間隔、未応答時の停止と再送禁止、手動ヒントの進行、認識不確実時と予定外の盤面変化での停止を確認しています。

Windows の操作検証は引き続き Linux 上の Wine 9.0 と、専用の仮想デスクトップを使用しました。Windows 実機、実際のブラウザゲーム、複数モニターと異なる表示倍率を組み合わせた実機構成は未検証です。

### GUI と再生間隔

`test_gui_windows` で、メニューバーの存在、旧ファイル操作ボタンの撤去、960×720 の最小サイズで主要操作部品が重ならないことを確認しました。Wine では他プロセスのメニュー項目情報を取得できなかったため、その環境に限って項目列挙の検査をスキップしました。通常の Windows で同テストを実行する場合は項目列挙も必須です。

上下操作による 0.1 秒ずつの変更、不正な数値からの復帰、再生中の 1.0 秒から 0.1 秒への変更、停止後に手順が進まないことを確認しました。今回の試行では変更後の 5 手の進行が約 518ms、探索取消が約 330ms、探索中の終了が約 2,025ms でした。取消時には 77 手の手順を保持しました。これらはこの環境の観測値です。

### 画面取得とクリック入力

`test_desktop_windows` は別プロセスの専用ゲームウィンドウを起動し、そのウィンドウだけに実際の `SendInput` を送ります。初期盤面とクリック後の盤面の画像認識、ヒントによってフォーカスが移らないこと、ヒントを通して指定マスへクリックが届くことを確認しました。

範囲外の座標、対象ウィンドウの移動、他のウィンドウによる被覆、前面の変更、プロセス ID の不一致、終了済みウィンドウはすべて拒否され、拒否後に追加のクリックが届かないことも確認しました。画面操作テストは私用の画面や既存アプリを操作せず、テスト自身が起動した対象だけを使用しています。

### アプリ全体を通した画面操作

最終版の `test_screen_gui_windows` は、実際の範囲指定をドラッグ入力で行い、認識、探索、操作、停止までを検証して終了コード 0 で完了しました。Wine 9.0、Xvfb、アプリの指定座標を尊重する設定の TWM を使用しています。

| シナリオ | 確認結果 |
|---|---|
| 自動操作で全消し | 200枚の盤面を76クリックで全消し。実クリック数と手順一覧の76手が一致し、範囲外へのクリックは0回。 |
| ヒント表示 | 600msの待機中に自動クリックが0回。リングを通した手動クリック1回で次の表示へ進み、Escでリングが消えることを確認。 |
| 自動操作を途中でEsc停止 | 全消し前に停止し、停止確認後600msに追加クリックがないことを確認。 |
| 別ウィンドウへの切り替え | アプリを前面に戻すと自動操作が停止し、停止確認後600msに追加クリックがないことを確認。 |

この76手はテスト時に得られた全消し手順で、真の最短手数を証明したものではありません。テストの600msは停止後の観察時間であり、停止に要する時間の保証値ではありません。

前面化は別プロセスへの通知が完了してから確認するようにしました。また、範囲選択はマウスイベントに記録された座標を使用し、描画待ちでイベントが遅れてもドラッグ開始位置を保持します。範囲選択用の画面を閉じた後に指定範囲を撮影し直してから認識するため、選択開始時の古い画像で操作を開始しません。

範囲選択と最小化の検証では、仮想画面のウィンドウ管理も必要です。最終検証はTWMの `UsePPosition "on"` で指定位置を維持する環境に揃えました。画面取得が一致しなかった試行でも、盤面の照合によりクリックを開始せず停止することを確認しています。
